# V1.2 RAW OCIO Release Gate

## Scope

V1.2 is ready only when RAW import, decode provenance, OCIO transform execution, analysis trust, UI diagnostics, and packaged runtime dependencies all pass together.

## Runtime Dependencies

- FFmpeg: packaged as a Tauri sidecar through `src-tauri/tauri.conf.json`.
- FFprobe: packaged as a Tauri sidecar through `src-tauri/tauri.conf.json`.
- BRAW bridge: packaged as a Tauri sidecar through `src-tauri/tauri.conf.json`.
- REDline: packaged as a Tauri sidecar through `src-tauri/tauri.conf.json`.
- OCIO config: discovered from `OCIO`, then bundled resources at `ocio/config.ocio`, `aces/config.ocio`, or `config.ocio`.
- OCIO processor: discovered from `CINEFLOW_OCIO_PROCESSOR`, then bundled resources at `bin/oiiotool` (preferred; supports `--colorconfig`/`--colorconvert` and can read the JPEG/PNG frames the app analyzes) or `bin/ocioconvert`.
- OCIO/OpenImageIO/LibRaw dylib dependency closure: bundled at `resources/lib/*.dylib`, rewritten to carry no `/opt/homebrew` runtime references.
- LibRaw bridge: discovered from `CINEFLOW_LIBRAW_BRIDGE`.

Do not add an `externalBin` entry for a binary that is not present in `src-tauri/bin`; Tauri packaging should fail loudly only after the binary is intentionally bundled.

## macOS Runtime Validation

Run `npm run verify:macos:v12` after `npm run build:direct`.

The validator requires the macOS `.app`, `.dmg`, FFmpeg, FFprobe, BRAW bridge, REDline, and bundled camera/look resources to be present. It reports OCIO config, `ocioconvert`, and LibRaw frame-decode bridge as blocked gates until those assets are intentionally added.

## macOS Runtime Asset Staging

Run `npm run stage:macos:v12-assets -- --ocio-config <path> --ocio-processor <path> --libraw-bridge <path>` to stage approved local runtime assets before rebuilding the package.

Staging destinations:

- `src-tauri/resources/ocio/config.ocio`
- `src-tauri/resources/bin/oiiotool` or `src-tauri/resources/bin/ocioconvert`
- `src-tauri/resources/bin/libraw_bridge`

The backend discovers both root resource paths and the nested `resources/...` layout produced by the current Tauri bundle mapping. This keeps source staging, package validation, and runtime diagnostics aligned.

Staged binaries and dylibs are frequently copied from Homebrew installs, which are read-only (`444`). `fs::copy` cannot overwrite an existing read-only destination, so a stale `target/*/resources/**` copy from before staging will break `cargo check`/`cargo build` with a `Permission denied (os error 13)` in `tauri-build`'s `copy_resources` step on the next rebuild. Stage with write permission intact (`chmod u+w`) so incremental rebuilds keep working.

## macOS Code Signing (App Store)

`scripts/production/mac_sign_and_package.sh` re-signs the Tauri-built `.app` for Mac App Store submission and produces `builds/CineFlow_Suite_SUBMISSION.pkg`. It must run against a `.app` built with plain `npx tauri build` (bundle id `com.exposeu.cineflow`) — **not** `npm run build:direct`, which overrides the identifier to `com.exposeu.cineflow-direct` and will not match the App Store Connect record or `src-tauri/embedded.provisionprofile`.

Two requirements the script depends on, both easy to silently regress when new sidecar/resource assets are added:

- **Every nested Mach-O binary and dylib must be signed before the main app** (frameworks → libs → OCIO/OIIO/LibRaw resources → sidecars → app), or `codesign --verify --deep --strict` fails with `code has no resources but signature indicates they must be present` / `a sealed resource is missing or invalid`. When a new sidecar or dylib set is added under `Contents/Resources`, add a signing phase for it in this script.
- **Nested standalone executables (no `Info.plist` of their own) must be signed with `src-tauri/entitlements.child.plist`** (`app-sandbox` + `inherit` only), not a broader capability-granting entitlements file. Without `inherit`, a sandboxed helper with no bundle identifier cannot resolve its own sandbox container and crashes at launch (`SIGTRAP`, Console shows `Unable to get bundle identifier for container id <name>`). `inherit` makes it join the parent app's already-established sandbox instead. This applies to `ffmpeg`, `ffprobe`, `braw_bridge`, `REDline`, and now `oiiotool`/`ocioconvert`/`libraw_bridge`.

A MAS-signed, provisioned `.app` cannot be launched directly via `open`/Finder on a development Mac (`RBSRequestErrorDomain Code=5`) — that is expected sandbox/provisioning behavior, not a packaging defect. Full runtime confirmation of sidecar spawning requires TestFlight/App Store Connect processing or an Xcode-managed development-provisioned run.

## Startup Diagnostics

The app info surface must report:

- FFmpeg path and version.
- FFprobe path and version.
- BRAW bridge path and active state.
- OCIO config status and source.
- OCIO processor status and active state.
- LibRaw bridge decode status and active state.

## Release Checklist

- [x] Import picker accepts video, BRAW, vendor RAW, open camera RAW, and proxy-guided RAW extensions.
- [x] Each imported source receives a decode path label.
- [x] Open RAW remains provisional unless LibRaw frame decode is available.
- [x] Vendor/proprietary RAW remains behind vendor decode or operator proxy unless a legal decoder is available.
- [x] OCIO config and processor status are shown separately in Camera Match Lab.
- [x] Analysis metrics become trusted only after direct decode and successful OCIO frame transform.
- [x] Proxy analysis remains explicit and provisional unless product policy changes.
- [x] App info reports FFmpeg, FFprobe, BRAW, OCIO, and LibRaw diagnostics.
- [x] macOS installer package passes. `npm run build:direct` produces both the release `.app` and `.dmg` when run with host `hdiutil` access.
- [x] macOS package runtime validation passes for required sidecars and resources, including OCIO/LibRaw. `npm run verify:macos:v12 -- --strict` passes all required and RAW/OCIO gates.
- [x] macOS runtime asset staging path exists. `npm run stage:macos:v12-assets` stages approved OCIO/LibRaw assets into bundleable source locations without bundling fake or unlicensed binaries.
- [x] Runtime ACES/OCIO assets are bundled and configured. `resources/ocio/config.ocio`, `resources/bin/oiiotool`, `resources/bin/ocioconvert` are staged and packaged.
- [x] LibRaw frame-decode bridge is bundled and configured. `resources/bin/libraw_bridge` is staged and packaged; `probe_ocio_processor`/frame transform discover the nested `resources/...` bundle layout.
- [x] macOS App Store code signing passes deep/strict verification. `codesign --verify --deep --strict` on a `.app` built via plain `npx tauri build` (bundle id `com.exposeu.cineflow`) returns `valid on disk` / `satisfies its Designated Requirement`; `scripts/production/mac_sign_and_package.sh` produces a `.pkg` signed with the `3rd Party Mac Developer Installer` identity and a non-expired certificate chain.
- [ ] Windows build passes with sidecar binaries present and signed as required. Current sidecar check is missing `ffmpeg-x86_64-pc-windows-msvc.exe` and `ffprobe-x86_64-pc-windows-msvc.exe`.
- [ ] Astro docs are updated only after manual production approval.

## Validation Evidence

- `cargo test --manifest-path src-tauri/Cargo.toml` passes with 83 Rust tests.
- `cargo check --manifest-path src-tauri/Cargo.toml` and `cargo check --manifest-path src-tauri/Cargo.toml --features direct-dist` both pass.
- `npm run build` passes for the frontend production bundle.
- `npm run build:direct` passes when run with host `hdiutil` access and produces `src-tauri/target/release/bundle/macos/CineFlow Suite.app` (bundle id `com.exposeu.cineflow-direct`) plus a `.dmg`.
- Plain `npx tauri build` (no config override) passes and produces `com.exposeu.cineflow` — the identifier required for `scripts/production/mac_sign_and_package.sh` and App Store submission.
- `npm run verify:macos:v12 -- --strict` passes all required checks and all three RAW/OCIO gates (OCIO config, OCIO processor, LibRaw frame-decode bridge).
- `codesign --verify --deep --strict --verbose=4` on the App Store `.app` passes (`valid on disk`, `satisfies its Designated Requirement`) after: (1) extending `mac_sign_and_package.sh` to sign the OCIO/OIIO/LibRaw resources, and (2) signing nested standalone sidecars with `src-tauri/entitlements.child.plist` (`app-sandbox` + `inherit`) instead of a broader entitlements file that lacked `inherit` and crashed sandboxed sidecars at launch.
- `pkgutil --check-signature builds/CineFlow_Suite_SUBMISSION.pkg` reports a valid, non-expired `3rd Party Mac Developer Installer` certificate chain.
- Sandboxed `hdiutil create` fails with `Device not configured`; this is an execution-environment limitation, not an app packaging failure.
- `node scripts/production/verify_windows_sidecars.mjs` fails because `src-tauri/bin` does not contain Windows `ffmpeg` or `ffprobe` sidecars.

## Phase Update: Runtime Readiness Check

The app now exposes a V1.2 RAW / OCIO readiness report in Settings. It separates implemented behavior from runtime blockers:

- OCIO config and OCIO processor are evaluated separately.
- LibRaw frame decode is required before open camera RAW can become direct/trusted analysis.
- Windows packaging and Astro documentation remain manual approval gates.
- The report stays blocked until all runtime and manual gates pass.
